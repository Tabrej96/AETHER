Contributing to AETHER

AETHER is open-source under the Apache-2.0 license, created and maintained by Tabrej. Contributions are welcome — from bug reports to new capability engines. Every contribution must pass the same quality gates the project holds itself to: honest numbers, no fabricated claims, and tests that prove what they say.

Development setup

1. Fork and clone

git clone https://github.com/YOUR_USERNAME/anythingwithaether.git && cd AETHER
git remote add upstream https://github.com/Tabrej96/anythingwithaether.git

2. Install dependencies

npm install --legacy-peer-deps

--legacy-peer-deps is required on first install due to a peer-dep conflict with upstream ESR tooling. Subsequent installs are clean.

3. Verify the setup

npx tsx bin/aether.ts validate
npx tsx --test src/core/aether.test.ts

4. Run the dev server (optional, for website)

npm run dev   # if the React workbench exists
# or just open website/index.html in a browser — no server needed

5. Create a branch

git checkout -b feat/my-new-engine
# or
git checkout -b fix/bug-description

Code standards

License

All AETHER-native code is Apache-2.0. Do not introduce GPL/AGPL dependencies into the core. External engines under copyleft licenses must be integrated strictly out-of-process (HTTP/CDP).

No fabricated numbers

The single most important rule in this project: every number must be measured, reproducible, or explicitly labeled UNMEASURED with a reproduction command. No claim is accepted without evidence. If a test cannot be run, it does not exist.

TypeScript

  • Use ESM modules (import / export) — no CommonJS require()
  • Strict types: no any, use unknown with type guards
  • Prefer readonly for immutable data
  • Use descriptive names: computeGstInvoice() not calc()

Testing

  • Every new engine must have a test file in the same directory: src/core/foo/foo.test.ts
  • Use Node's built-in node:test and node:assert/strict
  • Tests must be deterministic: no random seeds, no network calls, no time-dependent assertions
  • Known-value tests for arithmetic: e.g. assertEquals(180000, computeGst(100000, 0.18))
  • Flake detection: run each suite twice in the certification pipeline

Documentation

  • Every new engine needs a docs/ page describing what it measures, how, and the command to reproduce
  • Provenance must be documented: what upstream project (if any) inspired it, what license that project uses, and what AETHER reimplemented
  • Add your engine to the programs.html listing with upstream credits
  • Update QUICKSTART.md if your engine has a CLI command

Website

  • All website pages use the shared website/styles.css
  • Keep pages self-contained: no external JS/CSS dependencies
  • All links must work — test locally before submitting
  • Add Apache-2.0 license notice and Tabrej credit to every page footer

Testing requirements

Mandatory checks before submitting a PR

# 1. Validate all components
npx tsx bin/aether.ts validate

# 2. Run the full test suite
npx tsx --test src/core/aether.test.ts

# 3. Run your specific engine's tests
npx tsx --test src/core/your-engine/your-engine.test.ts

# 4. Run the benchmark suite
npx tsx bin/aether.ts benchmark

# 5. (If applicable) Run with live provider
npx tsx bin/aether.ts programs --live

The quality gate

Every agent and skill must score 100/100 on the deterministic quality gate. The gate checks for:

  1. An executable verifier (the component can prove it works)
  2. A zero-regression assertion (the component proves it doesn't break)
  3. Secret handling (no API keys, credentials, or tokens in source)
  4. Crash-recovery depth (what happens when the runtime crashes mid-execution)

Pull request process

  1. Fork & branch: Create a feature branch from main. Use a descriptive name: feat/p16-shipping-calculations or fix/p05-snapshot-tokens.
  2. Implement: Write your code, tests, and docs. Follow the code standards above. Every new engine needs:
    • The engine file(s) in src/core/
    • A test file in the same directory
    • A docs page in docs/
    • An entry in website/programs.html (if it's a new program)
    • An update to QUICKSTART.md (if it has a CLI command)
  3. Run all checks: 
    npx tsx bin/aether.ts validate
npx tsx --test src/core/aether.test.ts
npx tsx bin/aether.ts benchmark
  4. Commit: Write a clear commit message. End with the attribution line: 
    feat(programs): add P22 — Distributed Execution Intelligence

Adds a distributed execution engine with work-stealing scheduling,
fault-tolerant checkpointing, and cross-node verification.

Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>
  5. Open the PR:
    • PR title: clear and descriptive
    • PR description: what, why, how, measured results
    • End PR description with: Generated with [Claude Code](https://claude.com/claude-code)
    • Link to any relevant issues
  6. CI checks: The automated tests must pass. If they don't, fix them before requesting review.
  7. Review: A maintainer will review for correctness, honesty of claims, test coverage, and license compliance. Address all review comments.
  8. Merge: Once approved and CI passes, a maintainer merges your PR.

Adding a new capability engine

If you want to add a new engine to AETHER, here's the checklist:

First, is it a first-party engine or an upstream integration? First-party engines (P10-P21 style) are original Apache-2.0 code. Upstream integrations study an external project and reimplement its strongest idea as native AETHER code, following the 12-step research process.

First-party engine checklist

  1. Create src/core/yourEngine/yourEngine.ts implementing the ProgramEngine interface
  2. Create src/core/yourEngine/yourEngine.test.ts with known-value assertions
  3. Register in bin/aether.ts with a CLI command and MCP tool name
  4. Add to website/programs.html or website/evolution.html
  5. Document in docs/ — include measured results and reproduction commands
  6. Update QUICKSTART.md with the new command
  7. Update README.md links table if a new page was added

Upstream integration checklist

  1. Clone the upstream repo and verify its license
  2. Read the architecture and extract the strongest idea
  3. Reimplement as native AETHER code (Apache-2.0)
  4. Document the upstream source, license, and what was extracted in NOTICE.md
  5. If the upstream license is AGPL/GPL, ensure integration is strictly out-of-process
  6. Write tests that prove your reimplementation matches the upstream behavior
  7. Benchmark against the upstream tool and record honest numbers
